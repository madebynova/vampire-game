# Releasing: browser build, Windows game, launcher

Three things get published, in three different ways:

| What | Where it lives | How players get it |
|---|---|---|
| **Website** (+ browser build later) | `website/` → GitHub Pages | visit the site |
| **Windows game** | a GitHub Release tagged `v0.1.0` | the **launcher** downloads it |
| **Launcher** | a GitHub Release tagged `launcher-v0.1.0` | player downloads it once from the website |

> **Status:** none of the three has been published yet. Everything below is the *plan and tooling*; the parts that
> were actually run are marked **(tested)** and the parts that need your machine or accounts are marked **(your step)**.

## The big picture: how an update reaches a player

```
 YOU                                  GITHUB                             PLAYER'S PC
 ───                                  ──────                             ───────────
 1. edit VERSION  →  0.2.0
 2. build the game (Godot export)
 3. tools/package_release.ps1  ──►  VampireGame-Windows-v0.2.0.zip
                                     VampireGame-Windows-v0.2.0.zip.sha256
 4. publish  ─────────────────────►  Release  "v0.2.0"
                                       (notes = the changelog)
                                                  │
                                    5. launcher asks GitHub: "latest release?"
                                       (api.github.com/repos/madebynova/vampire-game/releases)
                                                  │
                                    6. launcher compares  installed 0.1.0  vs  latest 0.2.0
                                                  │   "New update available" → player presses UPDATE
                                    7. downloads the zip to a temporary folder
                                    8. checks size + SHA-256 + unpacks to a staging folder
                                    9. checks the package really is 0.2.0 and contains VampireGame.exe
                                   10. refuses if the game is running
                                   11. swaps the folders; the old game is kept until the swap succeeds
                                   12. records 0.2.0  →  player presses PLAY
```

The player's **settings and saves are never touched**, see "Saves" below.

## Versioning (one source of truth)

- The game version is the file [`VERSION`](../VERSION) at the repo root: `MAJOR.MINOR.PATCH`, e.g. `0.1.0`, `0.2.0`,
  `0.10.0` (compared as numbers, so `0.10.0` is newer than `0.9.0`). Pre-1.0 convention: bump **MINOR** for a
  content update, **PATCH** for a fix.
- Everything else is *derived*:
  - the Git tag and release name (`v0.1.0`), the zip name (`VampireGame-Windows-v0.1.0.zip`) and the `VERSION` file
    inside the zip are generated by `tools/package_release.ps1` from `VERSION`;
  - the `.exe`'s file/product version in `export_presets.cfg` is copied from `VERSION` by `tools/sync_version.ps1`, and
    `package_release.ps1` and `python tools/check_repo.py` refuse to continue if they disagree.
- The launcher has its own number in [`launcher/VERSION`](../launcher/VERSION) and its own release tags (`launcher-v…`),
  so launcher releases never get mistaken for game releases.
- The website does not show a version number (its badge says "Task 1.8", the prototype's milestone). Mapping from
  milestones to versions is yours to decide; the first release is `0.1.0`.

## Publishing the first Windows release (0.1.0)

Prerequisite: Godot 4.8 with the matching **export templates** (see the README, "Windows build"). They are installed on the
development machine and the build has been exported and run for real; on a new machine install them once first.

```powershell
# 1. make the .exe/project version match VERSION, commit the result
./tools/sync_version.ps1
git add export_presets.cfg project.godot; git commit -m "Set version 0.1.0"

# 2. export the game  ->  build/windows/VampireGame.exe   (run from a clean, committed tree so the build matches a commit)
./tools/build_windows.ps1 -Godot "C:\Godot\Godot_v4.8-dev6_win64_console.exe"

# 3. (recommended, ~15 min) run all test suites inside an exported build
./tools/test_exported_build.ps1 -Godot "C:\Godot\Godot_v4.8-dev6_win64_console.exe"

# 4. package it  ->  dist/VampireGame-Windows-v0.1.0.zip  +  .zip.sha256
./tools/package_release.ps1

# 5. publish it as a GitHub Release (needs the gh CLI, logged in); the notes live in docs/release_notes/
./tools/package_release.ps1 -Publish -NotesFile docs/release_notes/v0.1.0.md
```

Step 5 can also be done by hand: GitHub → *Releases* → *Draft a new release* → tag `v0.1.0` (create on publish) →
attach **both** files from `dist/` → publish. Rules the launcher relies on:

- the tag must be exactly `v` + the version (`v0.1.0`);
- the release must have **both** `VampireGame-Windows-v0.1.0.zip` and `VampireGame-Windows-v0.1.0.zip.sha256`
  (a release missing either is ignored, so a half-uploaded release can never reach players);
- do not tick *pre-release* or *draft* unless you mean it: the launcher skips both;
- the **release notes** are shown to players as the changelog.

Zips and `.exe` files are git-ignored (`dist/`, `*.zip`, `*.exe`): **never commit builds**; Releases are the place for them.

### What the package looks like

`VampireGame-Windows-v0.1.0.zip` has the game at the zip root (a single top-level folder also works):

```
VampireGame.exe      the Godot export (the game data is embedded in it, see export_presets.cfg)
VERSION              "0.1.0", added by package_release.ps1; the launcher checks it matches the release
README.txt           a short note for players who download the zip by hand (how to run, SmartScreen, settings)
```

## Publishing the launcher

```powershell
python -m pip install pyinstaller              # (your step, once)
./launcher/build_launcher.ps1                  # -> launcher/dist/VampireGameLauncher-v0.1.0.exe  (not yet run)
```

Run the exe once yourself, then publish a GitHub Release tagged **`launcher-v0.1.0`** with that exe attached. Then make the
website button live: in `website/index.html` set

```html
<html lang="en" data-play-url="" data-launcher-url="https://github.com/madebynova/vampire-game/releases/download/launcher-v0.1.0/VampireGameLauncher-v0.1.0.exe">
```

and re-deploy the site. Until then the button honestly says **Coming soon**.

Heads-up: an unsigned `.exe` triggers Windows **SmartScreen** ("Windows protected your PC"). Players can choose
*More info → Run anyway*. Removing the warning needs a code-signing certificate, which is a future step.

## Saves and settings (why updates don't wipe them)

The launcher only ever replaces **one folder**: the `game\` folder of its install root.

```
%LOCALAPPDATA%\VampireGame\          launcher install root (changeable before the first install)
    game\                            REPLACED on every update: VampireGame.exe, VERSION, …
    launcher.json, release_cache.json   launcher's own tiny files, kept

%APPDATA%\VampireGame\   the game's user data. NEVER touched by the launcher
    settings.cfg                     the game's options today
    mods\                            user mods
    (saves will live here too)
```

Godot's `user://` folder is that second location. `project.godot` sets `config/use_custom_user_dir=true` and
`config/custom_user_dir_name="VampireGame"`, so it is `%APPDATA%\VampireGame\` regardless of the project's name or where
the game is installed. Verified with the real exported exe: it wrote `settings.cfg`, `logs\` and a `shader_cache\` there and
nothing beside the exe. Today the game stores only `settings.cfg` and mods (there are no save games yet). **Rule for the game
from now on:** write anything the player should keep to `user://`, never next to the `.exe`. A test in the launcher suite
(`test_install_then_update_keeps_saves`) installs 0.1.0, updates to 0.2.0 and proves a fake save and settings file survive.

## What the launcher checks (and what it doesn't)

Done and tested: only game releases (`vX.Y.Z`) from `madebynova/vampire-game`; download URLs must be that repo's release
assets; temporary download that is renamed only when complete; size and **SHA-256** must match; unpacking is "zip-slip"
safe (no path escapes, no links, size caps); the package must contain `VampireGame.exe` and a `VERSION` equal to the release;
refuses while the game is running; the old game is restored if the swap fails; leftovers from a crash are cleaned up
at the next start.

Not done yet, by design: the checksum file lives in the same release as the zip, so it protects against **corruption**,
not against someone who could replace *both* files (that would need a signature checked against a key baked into the
launcher; `install.install_release` is the one place to add it). The launcher cannot update itself yet. It cannot
move an existing install. Releases are fetched unauthenticated, so GitHub's rate limit (60 requests/hour per IP) applies.

## Automating the Windows build in CI (TODO, deliberately not faked)

A GitHub Actions workflow could run steps 1–4 on a tag push, but it needs things that are not decided/available yet:
the exact Godot **4.8-dev** binary and its **export templates** (development builds are not in the usual Docker
images), the same `Windows Desktop (playtest)` preset, and a Windows or Linux runner able to run `godot --headless
--export-release`. Once those are pinned, the job is: checkout → download Godot + templates → `./tools/build_windows.ps1`
→ `./tools/package_release.ps1 -Publish`. Until then, release from your own machine as above. The existing
`.github/workflows/ci.yml` only runs checks that need no Godot.
